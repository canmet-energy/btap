## D-81 — The R3 primacy flip: the Python implementation is canonical and primary; the Ruby registry copy is generated; same-PR backports continue only until R4's verification handoff

**Decided:** The Python implementation is PRIMARY and CANONICAL
(2026-08-29). The decisive input: the Ruby gems have **zero users** — so
there is no support window, nothing to deprecate, and Ruby's only
remaining role is verification. It stays green solely as the Leg-B
cross-language baseline until R4 freezes Leg B's successor, and as Leg A's
bridge to the pinned oracle until R6.

**The registry authority reversed as MACHINERY, not policy text** (the
R1/R2 closure review's acceptance criterion for R3). Since this decision:

- `python/btap/necb/data/decisions.json` is the ONE hand-maintained
  registry; the copy at `btap-necb/lib/btap_necb/data/decisions.json` is
  GENERATED by `python/scripts/sync_decisions_registry.py` (direction
  reversed) and never hand-edited — byte identity is CI-enforced on every
  PR by a named lint gate plus the pytest sync test.
- The canonical editing workflow for a decision: (1) edit the canonical
  Python JSON; (2) author the `## D-XX` section here — the prose stays
  HAND-AUTHORED, never generated; the tests enforce id-set equality
  between doc and registry, not title/summary agreement; (3) run the sync
  to generate the Ruby copy; (4) regenerate the TOC; (5) run the Python
  registry/citation tests; (6) run the Ruby registry/TOC tests.
- The two-sided runtime-citation invariant is now enforced on BOTH sides:
  the Ruby test scans gem `lib/` as before, and a new AST-based Python
  scanner (`python/tests/necb/test_decisions_registry.py`) walks
  `python/btap` call keywords — literals only (no variable pass-through),
  on the audit surface only, docstrings and comments invisible by
  construction.
- **This entry itself landed through the new direction** — canonical JSON
  first, doc section authored, Ruby copy generated, TOC regenerated —
  which is the proof of the flip. A D-80 amendment was rejected precisely
  because amendment sub-headings are not mirrored into the registry and
  would have exercised none of the machinery.

**The working rule until R4's verification handoff:** a behaviour change
lands Python-first WITH its Ruby backport in the SAME PR, so Leg B stays
green at every commit. Backports stop only when the handoff completes —
the replacement scenario suite frozen and validated, the Ruby-vs-Python
Leg-B gates removed from required CI, their drivers dormant for R6
deletion — never merely when R4 "lands": stopping earlier would break the
still-wired gates on the first Python-only change.

**Not flipped here** (each has its own boundary): the decision doc's
location and the TOC generator (move together at R6; the generator
deliberately reads the GENERATED Ruby copy — byte identity makes those
the canonical bytes); the fixture-drift direction (Ruby tree
authoritative until R6); `packaging/windows`; the Ruby CLI's output
streams (R4 freezes them verbatim); Leg A's dispatch cadence.

**Distribution posture:** the README presents the Python implementation
as the product with an honest SOURCE install — the package is unpublished
(`0.1.0.dev0`, private repository), so `pip install btap` is reserved for
a future publication decision. The Ruby Windows installer remains
buildable but is no longer the recommended install; the native Python
installer is R5.

**Registry grammar ceiling:** ids are `D-NN` (two digits — D-99 is the
ceiling). Before allocating a hundredth decision, adjudicate the
successor id format and update the regexes, TOC sorting, registry tests,
and report parsing TOGETHER, in both implementations — the ceiling is
recorded WITH its transition rule so it defines a path, not just a
problem.

### Amendment — 2026-09-29: the per-decision source is canonical

The paragraphs above are the 2026-08-29 period record and stand as written.
Two of their machinery statements are superseded.

**Superseded:** that `decisions.json` is "the one hand-maintained registry",
and that the decision document's prose is hand-authored beside it. Both were
true of the R3 arrangement and of the R6 move that followed it.

**Now:** one decision is one file, `docs/decisions/D-NN.md`, carrying TOML
front matter (`id`, `title`, `kind`, `articles`, `summary`) and the authored
Markdown body. That file is CANONICAL. `docs/necb_decisions.md` and
`python/btap/codes/data/decisions.json` are both GENERATED from it by
`python3 python/scripts/generate_decisions.py`, and `--check` is the single
drift gate in CI. There is one writer, where R3's arrangement had the JSON
hand-maintained and the document's prose hand-authored against it, and R6's
had a second generator emitting the index alone.

**What did not change:** the Python runtime-citation invariant — a
`kind: "runtime"` entry is still cited by a `ruling:` tag in product Python.
The two-sided form named in the paragraphs above ended at D-84, which retired
the Ruby gem, so only the Python side is active. The paraphrase rule for
summaries is unchanged.

**What the migration moved.** No decision's text was rewritten, but the
partition is not uniform and an earlier wording of this paragraph stated one
that does not add up. Of the 97 bodies, 83 were carried byte-for-byte. Of the
remaining 14 — D-76 through D-89, authored without a heading title — 13
changed in their first line alone, each taking the registry title it already
carried in the index, and D-81 changed in its first line **and** by gaining
this amendment. In the registry, 96 entries are unchanged and D-81's summary
carries this amendment's substance: the registry's content moved exactly once,
here.

**Ordering.** Both generated artifacts are emitted in numeric id order. The
document previously claimed its entries were chronological and they were not:
document order, registry order and numeric order were three different
sequences, diverging over D-53…D-65, where entries dated 2026-08-02 preceded
entries dated 2026-07-29. Chronology is not a durable generator invariant — a
decision has an initial ruling, later amendments, and occasionally an id
reserved while another decision lands — so the claim is withdrawn rather than
repaired, and the index is titled by id order alone.

- **Who/when:** Sol ruled, 2026-09-29, on a survey that found the four
  conflicts above (heading text vs registry title, the three orderings, the
  registry's own key-order/escaping/array inconsistencies, and this preamble
  asserting the workflow the change repeals).
